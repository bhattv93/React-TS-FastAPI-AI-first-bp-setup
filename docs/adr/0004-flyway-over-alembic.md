# ADR-0004: Flyway for schema migrations, SQLAlchemy 2.0 as the ORM

- **Status:** Accepted
- **Date:** 2026-10-24

## Context

We use an ORM (SQLAlchemy 2.0, async) for data access. Schema migrations need to be reviewable, run the same
way locally, in CI and on AWS, and be owned by the database rather than generated by Python autogenerate.

## Decision

- **ORM:** SQLAlchemy 2.0 with typed `Mapped[...]` declarative models and async sessions (`asyncpg`).
- **Migrations:** [Flyway](https://documentation.red-gate.com/flyway) with plain SQL versioned migrations in
  `backend/db/migrations/` named `V<yyyymmddHHMM>__<snake_description>.sql`, plus `R__*.sql` for repeatable
  objects such as views.
- Flyway runs from the official `flyway/flyway` Docker image everywhere: local `docker compose`, CI, and an
  AWS pre-deploy task.
- **Applied migrations are immutable.** Changes go in a new migration. A Claude `PreToolUse` hook blocks edits
  to existing `V*.sql` files, and the Flyway checksum validation catches anything that slips through.
- An **ORM ↔ schema drift test** applies Flyway to a Postgres test DB and compares the reflected schema with
  `Base.metadata`. CI fails on drift.

## Alternatives considered

| Option | Pros | Cons |
|--------|------|------|
| Alembic | Python-native, autogenerate | Migrations coupled to Python; autogenerate output needs review anyway; team chose SQL-first |
| **Flyway** | SQL-first, DBA-friendly, language-agnostic, checksum validation | ORM and SQL can drift → needs the drift test; Community edition has no undo migrations |

## Consequences

- Tests run against **real Postgres** (Testcontainers locally, a service container in CI), not SQLite, because
  migrations are Postgres SQL.
- Rollback = forward-fix migration (Community edition has no `undo`). Document it in the runbook.
- The `new-db-migration` skill writes the SQL migration, updates the ORM model, and runs the drift test.
